# test-rust skill

## 目的

Rust ソースから純粋関数（および軽量にトレイトで切り離せる関数）を特定し、Rust 標準のテストフレームワーク（`#[test]` / `cargo test`）でユニットテストを生成・実行する。外部モックライブラリ（mockall等）は使用せず、標準機能のみで完結させる。

## 実行手順

### Step 1: 環境確認と対象ファイルの選定

**対象ファイル**: `src/**/*.rs`（ただし以下は除外）

| 除外パターン | 理由 |
|---|---|
| `target/**` | ビルド成果物 |
| `build.rs` | ビルドスクリプト、単体テスト対象外 |
| 既存の `#[cfg(test)] mod tests { ... }` ブロック内 | テストコード自身 |
| `tests/**` | 統合テスト（Step 5 で別途扱う） |

**ワークスペース対応**: ルートの `Cargo.toml` に `[workspace]` がある場合、`members` に列挙された各クレートを独立して扱う。各クレートの `Cargo.toml` を個別に参照する。

対象 Rust ファイルが見つからない場合は中断し、ユーザーに伝える。

### Step 2: コンパイル確認（cargo check）

```bash
cargo check --all-targets
```

を実行し、コンパイルエラーを検出する。

**エラーの扱い方**: Step 1 で選定したテスト対象ファイル（およびそこから参照されているファイル）に該当するエラーだけを必須要件にする。対象外ファイル（無関係なモジュール）のエラーは警告として残すが中断しない。

理由: 全体のコンパイルエラーで中断すると、テスト対象と無関係な箇所が原因でテスト生成が永遠に始まらない事態になる。

対象範囲にエラーがある場合は、エラー内容を報告して中断する（テスト生成より修正が先）。

### Step 3: 純粋関数の特定

各 `.rs` ファイルの `fn` / `pub fn` を対象に、以下条件を満たす関数を「テスト対象」として列挙する。

**テスト対象（純粋関数）の条件**:

- 引数のみに依存し、外部状態を参照・変更しない
- 同じ引数には常に同じ結果を返す
- 以下を含まない: `std::fs`（ファイルI/O）、ネットワークI/O（`reqwest` / `hyper` / `std::net` 等）、DBクライアント、`println!` / `eprintln!` 等の標準出力への副作用、グローバル可変状態（`static mut`、内部可変性を伴う `static` への書き込み）
- `unsafe` ブロックを含む関数は対象外とする（安全性検証はユニットテストの範疇を超えるため）

**トレイトで切り離し可能な関数**: I/O 依存がトレイト境界（`trait Repository { ... }` 等）で抽象化されている場合、テストコード側でフェイク実装（構造体 + トレイト実装）を定義してテスト対象に含める。フェイク実装の追加はテストコード内で完結し、元の実装は変更しない。

**async 関数の扱い**:

- `async` かつ内部が純粋な計算のみ（外部リソースにアクセスしない） → テスト対象に含める
- 外部リソースにアクセスする async 関数 → 除外
- `tokio` の `dev-dependencies` が `Cargo.toml` に無い場合、以下のメッセージで確認する（**自動追記はしない**）:

  ```
  非同期関数のテストには tokio の dev-dependency が必要です。
  Cargo.toml に以下を追加してください:

    [dev-dependencies]
    tokio = { version = "1", features = ["macros", "rt"] }

  追加後、再度 /test-rust または /test を実行してください。
  ```

  `Cargo.toml` への変更はユーザーが認知すべき変化のため、勝手に追記しない。

### Step 4: テストコードの生成（インラインユニットテスト）

Rust の慣習に従い、対象ファイルの末尾に `#[cfg(test)] mod tests { use super::*; ... }` ブロックを追加する（別ファイルに切り出さない）。

**既存テストブロックの扱い**: **上書きしない**。次のルールで部分更新する。

| 保護する部分 | 更新する部分 |
|---|---|
| 既存のテスト関数（`#[test] fn ...`） | 新規テスト関数をブロック末尾に追加 |
| 既存の `use` 文 | 不足分のみ追加 |
| 手書きのフィクスチャ・ヘルパー関数 | カバーされていない関数のテストを追加 |

理由: ユーザーが手書きしたテストやフィクスチャを勝手に消すと信頼を失う。テンプレートは「初回作成時の雛形」であり、運用が始まったテストファイルではない。

**生成するテストの形式（同期関数）**:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn 関数名_正常系() {
        assert_eq!(関数名(input), expected);
    }

    #[test]
    fn 関数名_境界値_空入力() {
        assert_eq!(関数名(...), ...);
    }

    #[test]
    fn 関数名_異常系_エラーを返す() {
        assert!(関数名(...).is_err());
    }
}
```

**`Result` を返す関数のテスト**（`?` 演算子を使う場合）:

```rust
#[test]
fn 関数名_正常系() -> Result<(), Box<dyn std::error::Error>> {
    let actual = 関数名(input)?;
    assert_eq!(actual, expected);
    Ok(())
}
```

**async 関数のテスト**:

```rust
#[tokio::test]
async fn 関数名_正常系() {
    let actual = 関数名(input).await;
    assert_eq!(actual, expected);
}
```

各テストケースは以下を網羅する:

- 正常系（代表的な入力）
- 境界値（空文字列 / 空配列 / `0` / 最大値・最小値 / `Option::None` など）
- 異常系（`Result::Err` を返す条件）

### Step 5: 統合テスト（該当する場合）

複数の内部関数を組み合わせて初めて意味のある振る舞いになる `pub` API は `tests/{クレート名}_integration.rs` への配置候補として提案する。

自動生成の対象は Step 4 のユニットテストのみとする。統合テストはテスト範囲の設計判断を要するため、候補を提示してユーザーに確認してから生成する。

### Step 6: テスト実行

```bash
cargo test
```

ワークスペースの場合は `cargo test --workspace` を実行する。

### Step 7: 結果報告

`/test` スキルから呼ばれた際にも解釈しやすい形式で報告する。最初の行を「テスト結果: X tests, X passed — OK」形式にして `/test` の Step 3 と整合させる。

`cargo test` の出力（`test result: ok. 12 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out`）をこの形式に変換する。

**全テスト pass の場合**:

```
テスト結果: X tests, X passed — OK
生成ファイル:
  - src/utils/format.rs（3 関数、8 ケース、mod tests に追加）
  - src/lib/calc.rs（2 関数、5 ケース、mod tests に追加）
```

**テスト失敗の場合**:

```
テスト失敗: X tests, X passed, X failed

失敗したテスト:
  ✗ tests::関数名_境界値_空入力: assertion `left == right` failed
      left: ...
      right: ...
```

失敗の原因が「生成したテストコードのバグ」か「実装側のバグ」かを切り分ける:

- テストコード起因（期待値の誤算、アサーションの取り違え、`use` 漏れ等）→ 自動修正して再実行
- 実装起因（関数の挙動が想定と違う）→ そのまま失敗を報告して中断。`/refactor` や手動修正を促す

修正サイクルが 2 回を超えても通らない場合は、それ以上ループせずユーザーに報告して中断する（テストコードのバグ修正と称して実装バグを覆い隠さないため）。

**純粋関数が見つからなかった場合**:

```
純粋関数が見つかりませんでした。
I/O依存が多い場合は /refactor でロジックを分離するか、トレイトによる抽象化を検討してください。
```
