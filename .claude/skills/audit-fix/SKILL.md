# audit-fix skill

## 目的

`docs/audit-plan.md` の指定重要度の項目を読み、確認なしに安全に修正できるものを自動修正する。
修正後は `audit-plan.md` のステータスを更新し、`docs/CHANGELOG.md` に変更を記録する。

## 引数

| 引数 | 対象重要度 |
|---|---|
| `ch` | Critical / High |
| `ml` | Medium / Low |

引数が指定されていない場合は処理を中断し、`/audit-fix ch` または `/audit-fix ml` のいずれかを指定するよう伝える。

## 絶対原則

1. **audit-plan.md が存在しない場合は中断**し、先に `/audit-plan` を実行するよう伝える
2. **引数で指定した重要度のみ修正する** — それ以外の重要度・Performance には触らない
3. **「確認不要」の判定はゲート方式のチェックリスト（後述 Step 2）で機械的に行う** — 形容詞による主観判断はしない。ゲートやパターン表で機械的に判定できない場合のみ要確認とする
4. **修正後は必ず audit-plan.md のステータスを更新する**

## 実行手順

### Step 0: 前提チェック

以下のいずれかに該当する場合は、修正処理に入らず早期終了する:

| 状況 | 対応 |
|---|---|
| `docs/audit-plan.md` が存在しない | 「先に `/audit-plan` を実行してください」と伝えて終了 |
| 引数が `ch` / `ml` のどちらでもない（未指定含む） | 正しい引数を案内して終了 |
| 対象重要度の項目が 0 件（そもそも該当カテゴリの記載がない） | 「対象項目はありません」と報告して終了。CHANGELOG への追記も不要 |
| 対象重要度の項目すべてに既にステータスマーク（`✅` `⏸` `🟡`）が付いている | 「未処理の対象項目はありません」と報告して終了 |

早期終了したケースでは Step 5 / Step 6 を実行しない（空エントリで CHANGELOG を汚さないため）。

### Step 1: 引数確認と対象抽出

引数を確認し、対象重要度を決定する:
- `ch` → Critical / High
- `ml` → Medium / Low

`docs/audit-plan.md` を読み、ステータスマーク（`✅`, `⏸`, `🟡`）のない対象重要度の項目をリストアップする。
各項目に対して「確認不要か / 要確認か」を後述の基準で分類する。

### Step 2: 確認不要 / 要確認の判定（ゲート方式）

判定は形容詞（「明らか」「自明」「リスクが否定できない」等）による都度の主観判断ではなく、**共通ゲート → パターン表（ホワイトリスト）**の2段階を機械的に適用する。

**適用順序（各 finding ごとに）**:

1. 共通ゲート G1〜G6 を上から順に評価する。**いずれか1つでも「該当したら」列の条件に一致した時点で判定を打ち切り、要確認とする**（以降のゲートは評価不要）
2. 全ゲートを通過したら、対象重要度（ch/ml）のパターン表を確認する。該当パターンがあれば**確認不要**、無ければ**要確認**とする（パターン表はホワイトリストであり、表にない finding を「似ているから」と類推適用しない）
3. ゲート自体の判定に必要な情報（grep結果、audit-planの記述内容）が不足・曖昧で機械的に white/black を決められない場合は、無理に推測せず要確認とする

#### 共通ゲート（ch / ml 共通）

| # | チェック内容 | 確認方法 | 該当したら |
|---|---|---|---|
| G1 | audit-plan.md の「対応」欄に、修正後のコードが一意に定まる形で書かれているか（方針レベルの曖昧な記述でないか） | 「対応」欄を読む | **書かれていない**なら要確認 |
| G2 | 修正が単一ファイル内で完結するか | 「対応」欄と該当コードを確認 | **複数ファイルにまたがる**なら要確認 |
| G3 | 変更する識別子（関数名・変数名・プロパティ名・export名）をプロジェクト全体で Grep し、宣言箇所以外の参照箇所すべてが今回の修正内容と矛盾しないか | Grep実行 | **矛盾する参照が1件でもある**、または**Grep自体ができない（動的な文字列経由アクセス等）**なら要確認 |
| G4 | 関数のシグネチャ（引数の数・順序・型、戻り値の形）を変更するか | 「対応」欄と該当コードを比較 | **変更する**なら要確認 |
| G5 | 認証・権限判定、外部通信（`UrlFetchApp` 等）、永続化（`PropertiesService` / シート書き込み等）、金額・数量計算ロジックのいずれかに触れるか | 該当コードのAPI呼び出し・計算式を確認 | **触れる**なら要確認 |
| G6 | audit-plan.md 記載時点のコードと現在のコード（Read した内容）が完全一致するか | Read | **一致しない**なら要確認（「コードが既に変更されている」として記録） |

#### ch（Critical / High）のパターン表（全ゲート通過後に適用）

| パターン | 変換前 → 変換後 | 機械的判定基準 |
|---|---|---|
| await漏れ | `someAsyncFn()` → `await someAsyncFn()` | 呼び出し先が `async` 宣言、または JSDoc `@returns {Promise<...>}` と確認でき、戻り値未使用の呼び出しに `await` を追加するのみ |
| 空catch | `catch (e) {}` → ログ出力+再スロー等 | catch ブロックの中身が空、またはコメントのみ |
| 識別子の参照ミス | typo した変数名・プロパティ名の修正 | 同一スコープ内に「意図した名前」の宣言が存在し、G3 の Grep で typo した名前の参照が当該箇所以外に0件（＝未定義エラーの直接原因） |
| typeof文字列比較漏れ | `typeof x === undefined` → `typeof x === "undefined"` | 左辺が `typeof` 式、右辺が文字列リテラルでない比較 |
| 未使用変数削除 | 孤立した `let x = ...` の削除 | G3 の Grep で宣言行以外の参照が0件 |
| non-null化 | オプショナルチェーン / null ガード追加 | audit-plan の「問題」欄にクラッシュ条件（どの入力で TypeError になるか）が具体的に記載されている場合のみ |

#### ml（Medium / Low）のパターン表（全ゲート通過後に適用）

| パターン | 変換前 → 変換後 | 機械的判定基準 |
|---|---|---|
| デッドコード削除 | 孤立した関数・未使用 import の削除 | G3 の Grep で宣言以外の参照が0件 |
| コメント/識別子typo | `recieve` → `receive` | 変更対象が識別子・コメント文言に限定され、ユーザー向け文字列リテラル（画面表示・エラーメッセージ）を含まない |
| コメント実装乖離修正 | 古い説明コメントを実装に合わせる | コメント文言のみ変更し、コード自体は変更しない |
| マジックナンバー定数化 | リテラル値 → `const NAME = 値` | G3 の Grep で同一リテラルの出現箇所を全て洗い出し済みで、置換漏れがない |
| nullチェック追加 | `if (x)` → `if (x != null)` | audit-plan に「0 や空文字が誤って falsy 判定される」等、具体的な誤判定条件が記載されている場合のみ |
| 重複コードのextract | 2箇所以内の重複を共通化 | G3 の Grep で重複箇所が正確に2件以内と確認でき、分岐なしでそのまま関数化できる（引数化不要） |

パフォーマンス問題（Performance カテゴリ）・責務分離やAPI変更を伴うリファクタリングは、この Step 2 の対象外（ch/ml いずれのパターン表にも存在しない）であり、常に要確認となる。

### Step 3: 修正の実行

確認不要と判定した項目のみ修正する。各項目で以下の流れを踏む。

**修正前チェック**

1. 該当ファイルを Read する（行番号ではなく該当コードの内容を直接確認する）
2. G6 を再評価する（Step 2 の時点から、同じ実行内で先に処理した他項目の修正によりコードが変わっている可能性があるため）。食い違っていれば修正せずスキップし、「コードが既に変更されているため要確認」として記録する
3. 該当箇所が既に他の修正で解消されている場合もスキップする

**修正の実行**

- 修正は**最小限**にとどめる（問題箇所のみを変更し、周辺コードには触れない）
- 一つの項目で複数ファイルにまたがる場合、全箇所修正してから次の項目へ

**修正後チェック**（呼び出し元への波及確認）

- 関数名・変数名・型名のシグネチャを変えた場合は、その識別子を grep して全呼び出し元が新しい形に整合しているかを確認する
- import / export を変えた場合は他ファイルから参照されていないかを確認する
- 整合しない呼び出し元があった場合は、その項目の修正をロールバック（元のコードに戻す）して `[波及確認] 修正後にロールバック` としてスキップ記録する。中途半端な状態を残さない

### Step 4: audit-plan.md のステータス更新

修正した各項目に `✅ 修正済 (YYYY-MM-DD)` を追記する。
スキップした項目には手を加えない。

### Step 5: CHANGELOG.md への記録

`docs/CHANGELOG.md` に以下の形式で追記する（ファイルがなければ作成）。

**修正が 1 件以上ある場合**（ch の例。ml も同形式で `M/L` に置換）:

```markdown
## YYYY-MM-DD — audit-fix ch

### 修正（C/H）
- [C-1] (問題タイトル): (何をどう直したか1行)
- [H-2] (問題タイトル): (何をどう直したか1行)

### スキップ（要確認）
- [C-2] (問題タイトル): [G4] シグネチャ変更を伴うため
- [H-3] (問題タイトル): [G6] コードが既に変更されているため要確認
```

スキップ理由には該当したゲート番号（`G1`〜`G6`）またはパターン表に非該当だった旨（`[パターン非該当]`）を先頭に付記する。理由を「要確認」のような曖昧な言葉だけで終わらせない — 後から見てどのゲートで止まったかが分かるようにする。

**修正が 0 件（全件スキップ）の場合**:

```markdown
## YYYY-MM-DD — audit-fix ch（自動修正なし）

全 N 件すべて要確認のためスキップ。詳細:
- [C-1] (問題タイトル): (スキップ理由)
- [H-2] (問題タイトル): (スキップ理由)
```

「修正」セクションが空のエントリは作らない（読み手が混乱するため）。

### Step 6: 完了報告

以下を報告する:

- 修正した項目数 / スキップした項目数のサマリ
- 修正した項目（ID・ファイル・内容）
- スキップした項目（ID・該当ゲート番号またはパターン非該当・具体理由）
- スキップ理由の内訳（どのゲートで止まったものが何件か）を集計して添える。特定のゲートに偏っている場合は、そのゲートの粒度が粗すぎる可能性があるとして次回 `/audit-fix` 実行時にユーザーへ再検討を促す
- スキップに「G6: コードが既に変更されている」「[波及確認] 修正後にロールバック」が含まれる場合は、その項目に注意喚起マークを付ける
- 「スキップ項目は手動での判断が必要です」と添える

修正が 0 件だった場合は、その旨を明示し、CHANGELOG にも「自動修正なし」エントリで記録した旨を伝える。
