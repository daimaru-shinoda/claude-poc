# refactor skill

## 目的

**単体テストを書きやすい構造**に変換する。
外部から見た振る舞いは変えず、内部構造のみを変える。

`/readable`（命名・コメント・型）とは異なり、コードの構造を変える。
`/audit-fix-*`（バグ修正）とは異なり、バグではなくテスタビリティの問題を対象とする。

## 絶対原則

1. **振る舞いを変えない**: リファクタ前後で外部から見た動作が同一であること
2. **テストで守る**: 既存テストがある場合は先に実行してベースラインを確立する
3. **期待値は必ず旧実装から導出する**: characterization test の期待値・テストケースは変換**前**のコードを読んで決める。変換後の実装を見てテストを書くと、変換時に混入したバグごと「正」として固定してしまう
4. **テスト追加を後回しにしない**: 抽出した関数のテストは同一変換サイクル内で追加する。「後で /test を実行して追加」という無防備な期間を作らない
5. **小さく変える**: 1変換 = 1ファイル or 1関数。巨大な一括変更はしない
6. **迷ったら止まる**: 「この変換で振る舞いが変わらないか」が自明でない場合は変換しない

## テスタビリティ問題のパターン

### 対象（変換してよい）

| パターン | 問題 | 変換方針 |
|---|---|---|
| I/O とロジックの混在 | 変換ロジックだけテストしたいのに外部リソースが必要になる | ロジック部分を純粋関数として抽出する |
| グローバル API の直接呼び出し | GAS なら `SpreadsheetApp`、Node なら `fs` など | 引数として受け取るか、依存オブジェクトを注入する |
| 巨大関数（50行超） | テストケースが爆発する、境界値が見えにくい | 責務ごとに関数を分割する |
| ハードコードされた定数 | テストで値を差し替えられない | 引数または定数定義に切り出す |
| グローバル変数への依存 | テスト間で状態が汚染される | 引数経由で受け渡す |

### 非対象（変換しない）

| パターン | 理由 |
|---|---|
| アルゴリズムの変更 | 振る舞いが変わるリスクが高い |
| エラーハンドリングの追加・変更 | バグ修正であり `/audit-fix-*` の責務 |
| 3箇所以上にまたがる共通化 | 影響範囲が広く設計判断が必要 |
| インターフェース（公開API）の変更 | 呼び出し元への影響が不明 |

## 実行手順

### Step 1: ベースラインテストの実行

Skill ツールで `/test` を呼び出し、現状のテスト結果をベースラインとして記録する。

リファクタは「外部から見た振る舞いが変わらない」ことが保証できて初めて意味がある。テストがそれを保証する唯一の自動手段なので、テストが無い・通っていない状態でリファクタすると、無自覚に振る舞いを変えるリスクが高い。そのため:

- **テストが存在しない場合**: 中断し、以下を伝える:

  ```
  テストが見つかりません。
  リファクタは振る舞いの保存をテストで担保するため、先に /test を実行してテストを作成してください。
  ```

- **テストが失敗している場合**: 中断し、先にテスト失敗を修正するよう伝える
- **テストが pass の場合**: 件数を記録（Step 6 の報告でリグレッション有無を判定するため）して Step 2 に進む

### Step 2: テスタビリティ問題の洗い出し

対象ファイルのソースコードを読み、前述のパターンに該当する箇所を列挙する。
各箇所について以下を記録する:

```
- ファイル:行番号
- パターン: (例: "I/O とロジックの混在")
- 変換方針: (例: "行列変換ロジックを parseRow() として抽出")
- 振る舞いが変わらない根拠: (例: "戻り値が同一、副作用は呼び出し元が担う")
- テスト先行可否: タイプA / タイプB（下記）
```

**テスト先行可否の分類**（Step 3 でサイクルが分岐する）:

| タイプ | 条件 | 例 |
|---|---|---|
| **A: 変換前からテスト可能** | 対象ロジックが既存の関数として呼び出せる（純粋関数の分割、引数注入、定数切り出しなど） | `isOverdue()` への時刻注入、巨大純粋関数の分割 |
| **B: 変換しないとテスト不能** | ロジックが I/O の内側に埋まっていて、抽出するまで呼び出す手段がない | `page.evaluate` 内の集計、コールバック内のインライン変換 |

振る舞いが変わらない根拠が書けない箇所は変換しない。

### Step 3: 変換の実行（1件ずつ、characterization test とセットで）

Step 2 でリストアップした箇所を**1件ずつ**変換する。サイクルは Step 2 のタイプで分岐する。
どちらのタイプでも共通する規律は2つ:

- **期待値は変換前のコードを読んで決める**（変換後の実装を見てテストを書かない）
- **テスト追加は同一サイクル内で完了させる**（後続の /test 実行に先送りしない）

#### タイプA: 変換前からテスト可能な場合 — テスト先行

1. 該当ファイルを Read する
2. **変換前の実装に対する characterization test を書き**、`/test` を呼んで pass を確認する（現行挙動のスナップショットを確立）
3. Edit で**最小限**の変換を行う（複数件をまとめて変換しない）
4. `/test` を呼ぶ
5. 結果で分岐:
   - **pass**: Step 2 で追加したテストが変換後も通っている = 振る舞い保存をテストが証明。「変換済リスト」に記録して次の件へ
   - **fail**: 変換を**ロールバック**して元のコードに戻す（Step 2 のテストは現行挙動に対して pass しているので残す）。再度 `/test` で pass を確認し、「スキップリスト」に記録して次の件へ

#### タイプB: 変換しないとテスト不能な場合 — 期待値表を先に固定

テストを物理的に先に書けないため、代わりに**期待値の導出を先に行う**ことで振る舞いの固定点を作る:

1. 該当ファイルを Read し、**変換前のコードだけを根拠に**「入力 → 期待される出力」の表を作る（境界値・null 経路・スキップ条件を含める）。この表が characterization の代替となる
2. Edit で**機械的な抽出**を行う（ロジックの分岐・式は1対1で移植し、書き換えない）
3. **同じサイクル内で**、手順1の期待値表をテストコード化して追加する
4. `/test` を呼ぶ
5. 結果で分岐:
   - **pass**: 抽出後の実装が旧コード由来の期待値を満たしている。「変換済リスト」に記録して次の件へ
   - **fail**: 期待値表とテストコードを再確認し、**期待値が旧コードの読みとして正しいなら抽出側のバグ**。変換と追加テストの両方をロールバックし（テストは存在しない関数を参照するため必ず一緒に戻す）、`/test` で pass を確認して「スキップリスト」に記録、次の件へ

このサイクルにする理由: (1) 複数件をまとめて変換すると失敗時の原因特定とロールバックが複雑になる。1件ずつなら「直前の1件が犯人」が常に確実。(2) テストを後で書く方式だと、抽出時に混入したバグを「正」として固定してしまい、characterization の意味がなくなる。

**変換例**

GAS — I/O とロジックの分離:

```js
// Before: SpreadsheetApp を直接呼ぶ関数はテスト不可
function processSheet() {
  const sheet = SpreadsheetApp.getActiveSheet();
  const data = sheet.getDataRange().getValues();
  return data.filter(row => row[0] !== '');  // ← このロジックだけテストしたい
}

// After: ロジックを純粋関数に抽出し、I/O は呼び出し元に任せる
function filterRows(data) {                   // ← テスト可能
  return data.filter(row => row[0] !== '');
}

function processSheet() {
  const sheet = SpreadsheetApp.getActiveSheet();
  const data = sheet.getDataRange().getValues();
  return filterRows(data);
}
```

JS/TS — 時刻依存の注入:

```ts
// Before: 定数がハードコード
function isOverdue(dateStr: string): boolean {
  const today = new Date();
  return new Date(dateStr) < today;
}

// After: 比較基準を注入してテスト可能に
function isOverdue(dateStr: string, today: Date = new Date()): boolean {
  return new Date(dateStr) < today;
}
```

TypeScript — 依存注入によるテスタビリティ向上:

```ts
// Before: fetch を直接呼ぶ関数はモック化が必要
async function fetchUserName(id: string): Promise<string> {
  const res = await fetch(`/api/users/${id}`);
  const user = await res.json();
  return user.name;
}

// After: 取得処理を引数で受け取れるようにして、ロジックだけテスト可能に
type UserFetcher = (id: string) => Promise<{ name: string }>;
async function fetchUserName(id: string, fetcher: UserFetcher): Promise<string> {
  const user = await fetcher(id);
  return user.name;
}
```

Python — グローバル状態を引数化:

```python
# Before: モジュールレベルの設定に依存していてテスト時に差し替えにくい
THRESHOLD = 10

def is_above_threshold(value):
    return value > THRESHOLD

# After: 閾値を引数で受け取る（デフォルトで既存の振る舞いを維持）
def is_above_threshold(value, threshold=THRESHOLD):
    return value > threshold
```

### Step 4: 全件完了後の最終確認

Step 3 を全件繰り返し終えたら、最後にもう一度 `/test` を呼んで全テストが pass のままであることを確認する。1件ずつ pass を確認しているので通常はここも pass のはずだが、変換間の相互作用で初めて顕在化するケース（例: 同じファイルへの 2 件の変換が組み合わさって挙動が変わる）を捕まえるための安全網。

万一 fail した場合は直近の変換から順にロールバックして原因を特定する。

### Step 5: CHANGELOG への記録

`docs/CHANGELOG.md` に以下の形式で追記する（ファイルがなければ作成）:

```markdown
## YYYY-MM-DD — refactor

### テスタビリティ向上
- `path/to/file.ts`: (変換内容1行)
- `path/to/file.ts`: (変換内容1行)

### テスト追加（characterization）
- `tests/xxx.test.ts`: (対象関数とケース数。タイプA=変換前に作成 / タイプB=旧実装の期待値表から作成 を明記)

### スキップ
- `path/to/file.ts:行番号`: (スキップ理由)
```

### Step 6: 完了報告

以下を報告する:

```
## リファクタ完了

### 変換済み
- path/to/file.ts: filterRows() を純粋関数として抽出（タイプB: 旧実装の期待値表からテスト5件を同時追加）
- path/to/file.ts: isOverdue() に today 引数を追加（タイプA: 変換前に characterization test 3件を作成して挟んだ）

### スキップ
- path/to/file.ts:45: processAll() — 呼び出し元3箇所に影響するため
- path/to/file.ts:120: handleX() — 変換後にテスト失敗、変換とテストをロールバック済み

### テスト
変換前: X passed / 変換後: Y passed（リグレッションなし。characterization test を Z 件追加）
```

報告に「次のステップとして /test でテストを追加してください」とは**書かない**。テスト追加はこのスキルの各サイクル内で完了しているのが正常な状態であり、未追加のまま終わるのは手順違反。

## 他スキルとの使い分け

| スキル | 対象 | ロジック変更 |
|---|---|---|
| `/refactor` | テスタビリティ（構造） | あり（振る舞いは不変） |
| `/readable` | 可読性（命名・コメント・型） | なし |
| `/audit-fix ch` | Critical / High バグ修正 | あり（振る舞いを修正） |
| `/audit-fix ml` | Medium / Low バグ修正 | あり（振る舞いを修正） |
