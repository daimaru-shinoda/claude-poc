# audit-plan skill

## 目的

**現コードベースに対する読み取り専用の監査**を別コンテキストで実施し、将来バグとして顕在化しうる実装・設計上のリスクを洗い出して `docs/audit-plan.md` に書き出す。
メインコンテキストを汚染しないよう、ファイルスキャンは Agent ツールのサブエージェントで実行する。

## 絶対原則

1. **別コンテキスト実行**: Agent ツールでサブエージェントを起動し、そこで監査を実行する
2. **Read-only**: 監査中はソースコードを一切変更しない（`docs/audit-plan.md` の作成・更新のみ許可）
3. **docs/audit-plan.md に記録**: 後工程（audit-fix）はこのファイルのみを参照する

## 実行手順

### Step 1: 対象ファイルの把握

Agent ツールを起動する前に、現在のプロジェクトのソースファイル一覧を把握する。
（Glob / Grep を使い、`src/` 等の主要ディレクトリと設定ファイルのパスを収集する）

既存の `docs/audit-plan.md` があれば内容を読み、継続監査として扱う旨をサブエージェントへ伝える。

### Step 2: サブエージェントの起動

Agent ツールを使い、以下のプロンプトをベースにサブエージェントを起動する。
`[ソースファイル一覧]` と `[既存audit-plan内容またはなし]` は Step 1 で収集した実際の値に置き換える。

**このスキルの Agent 呼び出しは必ず `model: "fable"` を指定する**（audit-plan 専用。他スキルのモデル指定には影響しない）。

```
コードベースの監査を実施してください。ソースコードは絶対に変更しないでください。
結果は docs/audit-plan.md に書き出します（docs/ ディレクトリが存在しない場合は作成してください）。

対象ファイル: [ソースファイル一覧]
既存 audit-plan.md: [既存audit-plan内容またはなし]

## 5観点でのチェック

各観点を順番に精査し、問題を見つけたら下記の重要度基準で分類する。

各観点には**言語非依存の観点**と**言語固有の例**を併記する。プロジェクトで使われていない言語の例はチェック対象から外し、別言語に同等の問題があればその言語の表現で記録する。例えば Python プロジェクトを監査するのに「`await` 漏れ」をそのまま当てはめるのではなく、`asyncio` のタスクが await されていないか、という形で読み替える。

### セキュリティ

言語非依存:
- 認証情報・APIトークン・パスワードがログ / エラーメッセージに出力されていないか
- ユーザー入力 / 環境変数のサニタイズ（CSVインジェクション、パストラバーサル、XSS、SQLi、コマンドインジェクション）
- ハードコードされた secrets、URL 内のクエリパラメータへのトークン埋め込み
- 外部送信前のバリデーション欠落
- 権限チェック漏れ、信頼境界の見落とし

### 正しさ

言語非依存:
- 非同期処理の部分失敗時の状態整合性、リトライなしの外部 API 呼び出し
- エラーの握りつぶし（空の例外ハンドラ、ログだけして握り潰すパターン）
- 競合状態、共有リソースへの並行書き込み、ロック忘れ
- 浮動小数点の等価比較、タイムゾーン、文字コード、ロケールの扱い
- 境界条件（空入力、null / 欠損値、0件レスポンス、最大長超過）
- 型のゆるさ・実行時型エラー（動的型付け言語での想定外の型流入）

言語固有の例:
- JS/TS: `await` 漏れ（fire-and-forget の Promise）、`catch {}` / `.catch(() => {})`、`any` の蔓延、型アサーション（`as`）の多用
- Python: 裸の `except:`、`asyncio` タスクの未 await、ミュータブル引数デフォルト
- GAS: `LockService` 未使用での同時書き込み、`PropertiesService` の値型を文字列以外と誤認
- Go: エラー無視（`_ =`）、goroutine リーク、`nil` ポインタ参照

### パフォーマンス

言語非依存:
- N+1 クエリ、ループ内の重い処理（外部 API 呼び出し、I/O、重い計算）
- 大量データのメモリ全展開（ページネーション・ストリーミング非対応）
- 不要な I/O（毎回書き出しては削除する、同一データの再取得）
- メモリ肥大（無制限に伸びるキャッシュ、配列への重複追加）
- 不要な同期ブロック、並列化可能処理がシリアル化されている

言語固有の例:
- JS/TS: ループ内 `await` でシリアル化、`Promise.all` の不使用
- Python: GIL を考慮しない並列化、`pandas` での行単位ループ

### 保守性

言語非依存:
- コード重複（同一ロジックが2箇所以上）
- デッドコード（未参照の変数 / 関数、未使用の依存）
- 責務混在（I/O + 変換 + 検証が1関数内）
- ハードコードされた値（環境依存の ID、URL、タイムアウト、閾値）
- コメント / docstring が実装と乖離
- テスト基盤の問題（flaky、実 API 依存のユニットテスト、共有状態を持つテスト）

言語固有の例:
- JS/TS: 意味不明な式（`typeof x === undefined`）、未使用 export
- 静的型付け言語: 型情報の欠落・`Any` 系型への安易な逃げ

---
## 重要度判定

「発生確率 × 影響度 × 検知しにくさ」で主観評価。迷ったら上位側に倒す。

| 重要度 | 目安 |
|---|---|
| Critical | セキュリティ事故 / データ破壊 / 本番停止に直結 |
| High | 影響のあるバグ / 運用中に再発しうる問題 / 明確な不具合 |
| Medium | 特定条件で顕在化 / 将来のリファクタで壊れやすい |
| Low | 軽微なコード品質問題 / 実害ほぼなし |
| Performance | パフォーマンスを明らかに悪化させる実装 |

## docs/audit-plan.md の出力フォーマット

既存ファイルがある場合は追記（新規 finding は既存 ID の続きから採番）。
無い場合は以下のテンプレートで新規作成。

```markdown
# システム監査レポート

**監査日**: YYYY-MM-DD
**対象**: (ファイルリストまたはパス)
**目的**: 将来バグとして顕在化しうる実装・設計上のリスクを洗い出す

重要度は Critical / High / Medium / Low / Performance の5段階。「発生確率 × 影響度 × 検知しにくさ」で主観評価。

---

## Critical

### C-1. (問題の1行タイトル)

- **該当**: `path/to/file.ts:行番号`
- **問題**: (具体的なコード引用 + 何が問題か)
- **影響**: (なぜ問題か、どのように顕在化するか)
- **対応**: (推奨修正方針)

## High
### H-1. ...

## Medium
### M-1. ...

## Low
### L-1. ...

## Performance
### P-1. ...

## 統計

- Critical: X件
- High: X件
- Medium: X件
- Low: X件
- Performance: X件

## 推奨修正順序

1. Critical / High の自動修正（/audit-fix ch）
2. テスト実行（/test）
3. Medium / Low の自動修正（/audit-fix ml）
4. テスト再実行（/test）
5. 可読性向上（/readable）
6. セキュリティチェック（/security-check）
7. 残存項目の手動対応
```

---
## 既存 audit-plan.md を更新する場合

- 新規 finding は既存 ID の続きから採番（例: 既存 C-2 まであれば新規は C-3 から）
- 過去の finding は削除せず、ステータスマークを追記する:
  - `✅ 修正済 (YYYY-MM-DD)` — 修正完了
  - `⏸ 現状維持 (YYYY-MM-DD, 理由)` — 検討の結果見送った
  - `🟡 部分対応 (YYYY-MM-DD)` — 一部修正、残作業あり
- 監査日と対象ファイルは冒頭に履歴として残す

---
## 出力品質のチェック

audit-plan.md を書き終えたら、送信前に自己レビューする:

- [ ] 各項目に `file:line` がある（指摘が再現できる）
- [ ] 「影響」欄が具体的で、why が説明されている
- [ ] Critical と High の件数が妥当か（Critical の乱発は信頼度を下げる）
- [ ] 同じ問題を重要度だけ変えて重複計上していないか
```

### Step 3: 完了確認

サブエージェントが `docs/audit-plan.md` を作成したことを確認する。
ファイルが存在しない場合は Step 2 を再試行する。

### Step 4: 完了報告

`docs/audit-plan.md` を読み、以下を報告する:

- `docs/audit-plan.md` の作成 / 更新を完了報告
- 件数サマリ（Critical: X, High: X, Medium: X, Low: X, Performance: X）
- **最優先で対応すべき項目を1〜3件**ハイライト（特に Critical）
