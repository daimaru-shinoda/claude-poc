# readable skill

## 目的

**ソースコードの可読性を向上させる**。バグ修正やロジック変更は行わない。
対象は以下の4観点のみ。

| 観点         | 内容                                                                  |
| ------------ | --------------------------------------------------------------------- |
| **タイポ**   | 変数名・関数名・コメント・JSDoc 内のスペルミスを修正                  |
| **命名規則** | プロジェクトの命名規則と乖離した識別子を修正                          |
| **コメント** | WHY コメントを追加・WHAT コメントを削除・実装と乖離したコメントを修正 |
| **型定義**   | JSDoc の `@param` / `@returns` / `@typedef` の欠落・誤記を修正・追加  |

## 絶対原則

1. **ロジックを変えない**: 実行時の挙動を変えないこと。許容される変更は以下のみ:
   - 識別子のリネーム（参照先も同時更新）
   - コメント / docstring の追加・削除・修正
   - 型注釈 / JSDoc の追加・修正
   - タイポ修正（識別子と非ユーザー向けコメントのみ。ユーザー向け文字列リテラルは原則対象外）
2. **WHY だけ書く**: コメントは「なぜそうするか」の非自明な理由のみ。実装が説明すれば書かない
3. **プロジェクト固有規約を最優先**: `CLAUDE.md` や言語標準のリンター設定に書かれた規約があれば、一般的な慣例より優先する
4. **テストを壊さない**: 識別子をリネームしたら、テストファイル含む全参照先を同時に更新する。Step 8 の `/test` で回帰を確認する

## 実行手順

### Step 1: 前提チェック（テストの存在確認）

リネームや型変更を安全に行うため、修正前にテストが通る状態を確認する必要がある。テストの存在確認と実行は `/test` スキルに委譲する（`/test` がプロジェクトの言語を動的に判別する）。

手順:

1. `/test` を呼び出して現状のテスト結果を取得する
2. `/test` が「テスト設定が見つかりません」を返した場合は以下のメッセージを伝えて**ここで処理を終了する**:

   ```
   テストが見つかりません。
   リネームや型変更の安全性を担保するためにテストが必要です。
   先に /test を実行してテストを作成してください。
   ```

3. `/test` がテスト失敗を返した場合も**ここで処理を終了する**。可読性改善の前にテストを通す必要がある:

   ```
   既存テストが失敗しています。
   readable はテストが通る状態を出発点としているため、先にテスト失敗を解消してください。
   ```

4. `/test` がテスト pass を返した場合のみ Step 2 に進む。Step 8 で再度 `/test` を呼んで回帰がないかを確認する。

### Step 2: 対象ファイルの特定

以下の優先順で対象ファイルを決定する:

1. **git リポジトリの場合**: `git diff --name-only HEAD` と `git diff --name-only --cached` の和集合（未コミットの変更）を対象にする。何も無ければ `git diff --name-only HEAD~1 HEAD` で直近コミットの変更を対象にする
2. **git が使えない場合**: 直近の会話で Read / Edit / Write したソースファイルを対象にする
3. **ユーザーが特定ファイルを指定した場合**: それを優先する

対象外（リストアップしても以下は触らない）:

- テストファイル（`tests/`, `*.test.ts`, `*_test.go` など。命名規則チェックのみ実施し、コメント追加・型定義追加はしない）
- ドキュメント（`docs/`, `*.md`, `README` 系）
- 自動生成ファイル（`dist/`, `build/`, `*.generated.*` など）
- 設定ファイル（`*.json`, `*.yaml`, `*.toml` — タイポチェックの対象外）

対象ファイルが 0 件なら、その旨を報告して終了する。

### Step 3: 命名規則の確認

命名規則は**プロジェクト固有のものを最優先**で適用する。把握の順序:

1. `CLAUDE.md` に命名規則の記載があるか確認する
2. 言語標準のリンター設定（`.eslintrc`, `pyproject.toml` の `[tool.ruff]`, `.golangci.yml` 等）があれば、その規則に従う
3. 上記がなければ既存コードの多数派に従う

#### 言語ごとの一般的な規則（参考。プロジェクト規約が優先）

| 種別 | JS/TS/GAS | Python | Go |
|---|---|---|---|
| 変数・関数 | camelCase | snake_case | camelCase（公開は PascalCase） |
| クラス・型 | PascalCase | PascalCase | PascalCase |
| 定数 | UPPER_SNAKE_CASE | UPPER_SNAKE_CASE | PascalCase or UPPER_SNAKE_CASE |
| プライベート | 規約次第（末尾 `_` を使うプロジェクトもある） | 先頭 `_`（`_name`） | 先頭小文字 |
| 真偽値 | `is` / `has` プレフィックス | `is_` / `has_` プレフィックス | 同左 |

#### 言語非依存のチェック項目

- [ ] 略語が不統一でないか（`msg` と `message` が混在など）
- [ ] 真偽値の識別子が真偽値らしい名前か（`is`/`has`/`should` 等のプレフィックス）
- [ ] 複数形・単数形が意味と一致しているか（`messages` vs `message`）
- [ ] プロジェクト固有の規約（CLAUDE.md 記載のもの）に従っているか — 例: プライベートメンバーの末尾/先頭マーク

### Step 4: タイポの修正

- 変数名・関数名のスペルミス（例: `contenType` → `contentType`）
- JSDoc・インラインコメント内のスペルミス
- 文字列リテラルは**意味が変わるため修正しない**（エラーメッセージ等も含む）

### Step 5: 型定義の追加・修正

CLAUDE.md の規約: **「関数 / クラスを作成するときにコメントで入出力の型と目的を明記する」**

型の表現方法は言語によって異なるため、対象ファイルの言語に合わせて使い分ける。

#### TypeScript / 型付き言語（Rust, Go, Kotlin 等）の場合

実コードの型注釈で表現する。JSDoc は不要（むしろ重複なので削除する）。

- [ ] 関数の引数・戻り値に型注釈があるか
- [ ] `any` / `unknown` / `interface{}` など曖昧な型に頼っていないか（具体型 or ジェネリクスで表現できないか）
- [ ] `null` / `undefined` を返しうる関数の戻り値が Union 型で表現されているか（TS: `T | null`、Rust: `Option<T>`、Go: `(T, error)`）
- [ ] 型エイリアス / インターフェースに意味のある名前があるか（`type Data = ...` ではなく `type ParsedMessage = ...`）
- [ ] 関数の目的を 1〜2 行のコメント / docstring で説明しているか（WHY、自明なら省略可）

例（TypeScript）:

```ts
/** trimTag 適用済みの本文を解析する。フォーマット不一致なら null */
function parseBody(body: string): ParsedMessage | null { ... }
```

#### JavaScript / GAS など型システムが弱い言語の場合

JSDoc で型と目的を明記する。

- [ ] すべての関数に `@param` と `@returns` があるか（`void` も省略しない）
- [ ] `@param` / `@returns` の型が実際の引数・戻り値と一致しているか（`null` を返す場合は `| null`）
- [ ] タプルや複雑なオブジェクトは `@typedef` で名前を付けているか
- [ ] `{Object}` など曖昧な型を使っていないか（具体的なプロパティ定義を推奨）
- [ ] クラスのコンストラクタに `@param` があるか

JSDoc の記述例:

```js
/**
 * 目的の説明（WHATではなくWHY。自明なら省略可）
 * @param {string} body trimTag 適用済みのメール本文
 * @returns {ParsedMessage | null} フォーマット不一致の場合は null
 */
```

#### Python の場合

型ヒント（PEP 484）と docstring を併用する。

- [ ] 関数の引数・戻り値に型ヒントがあるか（`def f(x: int) -> str`）
- [ ] `Optional[T]` / `T | None` で None 許容を明示しているか
- [ ] docstring に目的を 1 行で記述しているか（WHY）

### Step 6: コメントの整理

CLAUDE.md の規約: **「コメントは WHY を書く（WHAT は型・名前で表現し、重複して書かない）」**

#### 削除するコメント（WHAT コメント）

実装そのものを言い換えただけのコメントは削除する。

```js
// JS/GAS の例
// 既読に変える         ← message.markRead() が説明している
// 古いファイルを削除する ← setTrashed(true) が説明している
```

```ts
// TypeScript の例
// ユーザー名を取得する  ← getUserName() が説明している
// 配列を逆順にする      ← arr.reverse() が説明している
```

```py
# Python の例
# i に 1 を足す         ← i += 1 が説明している
# リストを返す           ← return [...] が説明している
```

#### 追加するコメント（WHY コメント）

非自明な制約・回避策・背景知識が必要な箇所のみ追加する。

```js
// GAS の例
// GmailLabel.addToThread() は1件ずつ呼ぶと Quota を消費するため
// addToThreads() でバッチ処理する
```

```ts
// TypeScript の例
// React 18 の StrictMode で effect が 2 回走るため、
// 多重実行を防ぐためのフラグを持っている
```

```py
# Python の例
# pandas の groupby は NaN を黙って捨てるので、
# 事前に sentinel 値に置換しないとレコード欠落する
```

#### コメントと実装が乖離している場合

実装を真実として扱い、コメントを修正または削除する。実装側を変えてコメントに合わせるのは readable の責務外（バグ修正であり `/audit-fix` の領分）。

### Step 7: 変更の適用

各 Step の変更をファイルに書き込む。

**識別子をリネームした場合の参照更新手順**:

リネームは局所的な置換ではなく、プロジェクト全体への影響を持つ。漏れがあると Step 8 のテストが失敗するか、より悪いケースとして実行時エラーになる。次の手順で参照を洗い出す:

1. **元の名前で grep**: プロジェクト全体（テスト・ドキュメント含む）で元の識別子を Grep する
   - 単独で意味を持つ識別子（`UserService` など）なら単語境界マッチ（`\b...\b` 相当）
   - 短い識別子（`id` `i` 等）は誤マッチが多いので、リネーム前にスコープを確認してからにする
2. **ヒットしたファイルを分類**:
   - **同一スコープの参照**: 同時に Edit で更新する
   - **JSDoc / docstring / コメント内の言及**: 同時に更新する
   - **文字列リテラル内の言及**: 動的に呼ばれている可能性があるため、機械的に置換せず**ユーザーに確認**する（`eval` や DI コンテナのキー、ログ出力等のケース）
   - **マークダウンドキュメント**: docs/ 配下は readable の対象外だが、リネーム時のみ参照先を直す
3. **同名の別物がないか確認**: 別ファイルで偶然同名の識別子が定義されていることもある。grep ヒットの周辺を読んで「これは本当に同じものを指しているか」を確認する
4. **import / export パスの更新**: ファイル名自体をリネームしていないなら不要だが、識別子名が export 名に含まれる場合は import 側も更新

リネームをまたいで Step 8 の `/test` が失敗したら、漏れた参照が原因なので grep をやり直す。

### Step 8: テストの実行（回帰確認）

`/test` スキルを呼び出して、可読性改善が既存テストを壊していないか確認する。

- pass の場合: Step 9 に進む
- 失敗の場合: Step 7 でのリネームや参照更新の漏れが原因である可能性が高い。失敗テストのエラーメッセージから不整合箇所を特定し、参照先を修正してから再度 `/test` を呼ぶ
- 修正してもなお失敗する場合は、その時点までの変更を**ロールバック**（直近の Edit を元に戻す）してユーザーに報告する。ロジックを壊した状態を残さない

### Step 9: ユーザーへの報告

変更内容を観点ごとに箇条書きで報告する。

```
## 変更サマリ

### タイポ修正
- ...

### 命名規則
- ...（問題なければ「問題なし」）

### コメント
- ...

### 型定義
- ...

テスト: X tests, X passed
```

## 出力品質のチェック

変更を適用してユーザーに報告する前に自己レビューする:

- [ ] ロジック（実行時挙動）を変えていないか
- [ ] リネームした識別子の参照先を全て更新したか（テストファイル含む）
- [ ] 追加したコメントが WHY を説明しているか（WHAT になっていないか）
- [ ] 戻り値が無い関数の型も明示したか（TS: `void`、JSDoc: `@returns {void}`、Python: `-> None`）
- [ ] `/test` が pass で完了したか
- [ ] CLAUDE.md のプロジェクト固有規約に従っているか
